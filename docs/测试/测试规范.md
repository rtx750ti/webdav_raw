# WebDAV Core 测试规范

## 目的

测试代码按 WebDAV 接口领域组织，让 GET、PROPFIND、认证各自维护自己的请求、响应、边界和覆盖线路。测试目录承载全部测试代码，`src` 只保留业务代码。

单元测试是本项目的重点。日常本地测试以单元测试为主，优先锁住边界值、序列化、反序列化和白盒路径；集成测试负责确认公开接口串联后的协议契约。真实 WebDAV 测试作为单独验收，不进入日常覆盖率门槛。

## 测试分层

测试先按领域划分，再按执行环境和职责划分。

```text
领域：auth / get / propfind / put
  ├─ local：本地离线测试
  │   ├─ unit：单元测试重点
  │   │   ├─ boundary：单个输入或输出边界
  │   │   ├─ serialization：序列化、反序列化和回环转换
  │   │   └─ whitebox：函数内部的独立路径和错误分支
  │   ├─ integration：接口完整流程
  │   └─ coverage：覆盖率报告中的遗漏分支（按需新建）
  └─ network：真实 WebDAV 验收
```

`local` 中的 MockServer 只监听本机回环地址，因此归入离线测试。它验证实际 HTTP 请求和响应，但不依赖互联网、账号或远端文件。

`network` 只在明确启用时连接真实服务，读取 `WEBDAV_URL`、`WEBDAV_ACCOUNT`、`WEBDAV_PASSWORD`。测试输出不得打印账号、密码、Authorization 或完整凭据。

## 目录与测试目标

```text
tests/
  auth/
    mod.rs
    common/
    local/
      unit/
        boundary/
        whitebox/
      integration/

  get/
    mod.rs
    common/
    support/
    local/
      unit/
        boundary/
        whitebox/
      integration/
    network/

  propfind/
    mod.rs
    common/
    support/
    local/
      unit/
        boundary/
        serialization/
        whitebox/
      integration/
    network/

  put/
    mod.rs
    common/
    support/
    local/
      unit/
        boundary/
        serialization/
        whitebox/
      integration/
    network/
```

`auth/mod.rs`、`get/mod.rs`、`propfind/mod.rs`、`put/mod.rs` 只登记子模块，不放测试用例。Cargo 将这四个模块注册为独立测试目标，以便单独运行某个领域。

每个领域各留一份自己的 `common/`，不跨领域共用同一份文件。集成测试是各自独立的 crate，跨目录共用一份文件只能靠 `#[path]`，而项目禁止 `#[path]`；把共用能力搬进 `src` 又会把 Mock 依赖带进正式环境。因此 Mock 启动与配置读取这类十几行的通用代码按领域重复，是本规范明确接受的代价。

`common/` 只能放通用 HTTP Mock、环境变量读取和通用断言。它不得包含 GET 路径规则、PROPFIND XML、认证业务判断或领域专属数据。

现有 PROPFIND XML 固件继续保留在 `test_files/propfind`；`tests/propfind/support/fixtures.rs` 使用编译期读取方式提供给本领域测试。GET、认证和 PUT 测试不得引用 PROPFIND 固件。

PUT 领域不依赖仓库自带的二进制夹具：文件源测试在系统临时目录现场造文件，用完即删。

## 单文件规则

每个测试文件只验证一个主题，文件名直接表达主题：

- `request_contract.rs`：只验证请求协议契约。
- `response_status.rs`：只验证状态码行为。
- `payload_conversion.rs`：只验证数据源到请求语义的转换。
- `streamed_file.rs`：只验证文件源的流式发送。
- `date.rs`：只验证日期解析和序列化边界。
- `parser_branches.rs`：只补 XML 解析的覆盖缺口。

一个文件可以有多个同主题用例。测试名称采用 `场景_预期结果` 的形式，例如 `empty_base_url_returns_empty_base_url_error`。

测试数据在测试内就近声明；同一领域反复使用的 Mock 构造和断言放入该领域的 `support`。测试之间不得依赖执行顺序、其他测试创建的数据或真实网络状态。

## 单元测试、集成测试和覆盖补点的职责

### 单元测试

单元测试是第一优先级。它从公开 API 调用单个领域能力，使用固定输入和固定断言，避免依赖真实网络和其他领域的测试数据。

每个领域的单元测试至少包含三类：

- `boundary`：验证空值、非法值、最小值、最大值、编码和状态边界。
- `serialization`：验证模型到协议文本、协议文本到模型，以及双向回环转换。
- `whitebox`：按函数控制流图覆盖每个独立路径、分支和错误返回。

序列化与反序列化的验收规则是双向可转换：

```text
模型 A → 序列化 → XML B → 反序列化 → 模型 A'
模型 A' 与模型 A 的资源数量、顺序和已支持字段一致

XML B → 反序列化 → 模型 C → 序列化 → XML D → 反序列化 → 模型 C'
模型 C' 与模型 C 的资源数量、顺序和已支持字段一致
```

XML 允许存在空白、命名空间前缀和属性顺序差异；测试比较模型语义，不比较 XML 字节文本。href、目录标记、内容长度、修改时间、MIME、ETag、状态码和响应顺序都属于模型语义。

`MultiStatus::from_str` 保留服务端返回的完整响应列表。`response_xml_roundtrip.rs` 以完整响应验证双向转换；后续如需要筛除当前目录，应由单独的列表处理能力完成，并有独立测试。

### 集成测试

集成测试只从公开接口进入，使用本地 MockServer 发出实际 HTTP 请求。它负责验证接口调用链：输入、请求方法、URL、请求头、请求体、状态码和公开返回值。

GET 集成测试验证 GET 请求和原始响应透传；PROPFIND 集成测试验证 PROPFIND 请求体、Depth、207 响应和 `MultiStatus` 结果。认证集成测试验证默认 Authorization 和 `get()`、`propfind()` 工厂入口；PUT 集成测试验证三种数据源的请求体字节、`Content-Length`、`Content-Type`、显式范围头和状态码透传。

PUT 的 `unit/serialization` 不涉及 XML 回环，验证的是数据源到请求语义的转换：字节与长度一致、元数据到请求头的映射、三种来源经 Builder 后语义一致。

### 覆盖补点测试

覆盖补点测试在单元和集成测试完成后创建。每个测试都必须在用例注释中写明覆盖率报告里遗漏的函数和条件分支。

覆盖补点只测试尚未覆盖的线路。优先把缺口补到本领域的 `unit/whitebox`；只有跨越完整 HTTP 链路才能命中的缺口才写入 `coverage`。例如集成测试已经命中 207 正常响应后，`coverage` 目录不再重写同一场景；若报告显示非法 XML 分支未命中，才在 `parser_branches.rs` 增加该用例。

## 本地与真实网络的执行规则

本地测试是默认测试集，必须在无网络、无账号、无真实 WebDAV 服务的环境中通过。它包括单元测试、本地集成测试和覆盖补点测试。

真实网络测试同时使用 `network-test` 功能开关和 `#[ignore]`。它们只在人工验收或受控流水线中运行，并验证指定服务的只读 GET、PROPFIND、不存在路径和错误认证响应。真实网络测试不创建、修改或删除远端资源。

PUT 会修改远端资源，因此默认只做本地 MockServer 验证，不新增日常真实网络 PUT 测试。`tests/put/network/` 只保留一个默认忽略的最小验收，且只在受控环境人工执行；真要跑之前必须先确定临时资源、清理责任和人工授权。

覆盖率门槛只使用本地测试的结果。真实网络测试用于确认特定服务兼容性，网络波动和服务端数据变化不影响日常覆盖率结论。

## 覆盖率规则

覆盖率统计范围是业务源码，测试代码、examples 和真实网络测试不作为业务覆盖率门槛。

验收门槛：

- 行覆盖率不低于 95%。
- 函数覆盖率不低于 95%。
- 区域覆盖率不低于 95%。
- 认证、GET、PROPFIND、PUT 的关键成功和错误分支全部命中。
- 文档示例全部通过编译。

覆盖率工具在落地阶段接入 `cargo-llvm-cov`。日常覆盖率命令不启用 `network-test`，并在覆盖率报告中按 `auth`、`get`、`propfind`、`put` 复查未命中行。新增业务分支先增加本领域单元测试；涉及完整请求协议时增加集成测试。报告仍有缺口时再增加覆盖补点测试。

## 提交前检查

每次测试改动完成后按顺序执行：

1. 运行当前领域的本地测试。
2. 运行全部本地测试。
3. 运行文档示例测试和 example 编译检查。
4. 运行覆盖率报告，确认三个指标均达到门槛。
5. 复查测试文件只触及所属领域，公共工具没有承载领域规则。

真实网络测试只在已配置受控环境并明确要求验收时执行。任何情况下均禁止执行 `git push`，暂存区只在明确授权后修改。
